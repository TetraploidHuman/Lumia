## 1. 设计宣言

Lumia 是一门 **以人类思维为表面语法、以编译器证明为性能基础** 的编程语言。

### 1.1 核心命题

1. **写像命令，义像数学** —— 用户按顺序书写程序，语义上仍是值导向、可推理的。
2. **函数式是默认，不是选项** —— 一等函数、代数数据类型、模式匹配、不可变优先；但不强迫用户学习范畴论。
3. **完全类型推断** —— 用户代码 **无需** 写任何类型注解；类型存在于编译器与错误信息中，不存在于日常书写中。
4. **严格求值** —— 执行顺序与直觉一致，拒绝全局惰性带来的空间泄漏与调试地狱。
5. **性能优化对用户零可见** —— 公共子表达式消除、逃逸分析、管道融合、按需物化、写时复制，全部由编译器完成；语言不提供 `pure`、`lazy`、`Stream`/`Array`、`HashMap`/`TreeMap` 等让用户操心性能的开关。
6. **可观测语义最小化** —— 用户只能依赖 **值的相等性** 与 **效应语句的执行顺序**；不能依赖分配时机、求值次数、内存地址、中间结构是否物化。
7. **效应由编译器认，不由用户标** —— 无强制 `pure`/`IO`/`effect` 注解；`main` 隐式可做 I/O；日常直接写 `println`，不包 `effect { }`。

### 1.2 非目标

- 不是 Haskell 的复刻：无全局惰性、无显式 Monad IO、无强制 `effect`/`do` 仪式、无“一切皆 Category”。
- 不是 C 的复刻：无裸指针、无未定义行为作为性能手段、无 `sizeof` 泄漏实现细节。
- 不是“多范式大杂烩”：无 `class` / 继承 / 对象同一性；数据统一用 `type`（积用 `val` 字段，和用变体），行为用函数与 `trait`。
- 不是“注解驱动”语言：类型注解不是常规写法；`fn foo(x = Int) -> Int` 这类签名 **不是** 用户默认风格。

### 1.3 设计口号

> **你只写程序。编译器负责证明它本可以更快。**
>
> **类型存在，但你不必写。**
>
> **效应存在，但你不必标。**
>
> **工具链目标平台：Linux 与 Windows**（见 [BUILD.md](BUILD.md)）。

## 2. 可观测语义契约

这是 Lumia 与用户之间的 **唯一合同**。所有优化必须保持下列可观测行为不变。

### 2.1 值语义

- 两个 Lumia 值 **相等**，当且仅当它们在语言定义的 `==` 下相等。
- `==` 是 **结构相等**（递归比较内容），不是引用相等。
- 语言 **不提供** 引用相等运算符（无 `===`、无 `is` 指同一性、无 `identityHashCode` 作为语言特性）。
- 浮点数相等遵循 IEEE 754；`NaN` 与自身不等。

### 2.2 效应语义

- **效应** 指：I/O、环境交互、非确定性、时钟、进程、网络、可变全局状态、调试观测点。
- **可观测副作用的最小单位是效应语句**（如一次 `println(...)`），不是「整个函数体」，也不是必须包一层的 `effect` 块。
- 效应语句按 **源码顺序** 依次执行；编译器不得重排、合并、删除效应语句。
- **效应上下文**（允许出现效应语句、调用效应函数）包括：
  1. **`main`（程序入口）** —— **隐式**效应根；体内直接写 I/O，无需 `effect { }`。
  2. **任意已推断为有效应的函数体** —— 函数因直接/间接效应而 `ε ≠ ∅` 后，其体即为效应上下文。
  3. **可选的 `effect { ... }`** —— 显式圈出一块效应区域；**不是日常必写**，见下。
- 纯表达式 / 纯函数体内 **禁止** 效应；若用户尝试，编译期报错。
- 模块顶层 `val` 的初始化表达式必须为 **纯**（顶层不跑 I/O；I/O 从 `main` 或由其调用的效应函数进入）。
- 函数级效应标签（见 §3.7）只约束 **谁能调用谁**；函数体内仍可交错纯计算与效应语句。编译器对体内无效应的子表达式按 **纯区域** 分析与优化，不要求用户为此拆函数。

#### 2.2.1 `effect { }` —— 可选，非常规税

- **默认写法**：在 `main` 或效应函数里直接写效应语句；用户 **不必** 手写 `effect`。
- **`effect { ... }` 可选保留**：仅用于想显式标注「这里按序做效应」的隔离块（例如在长函数里视觉分区）；语义上等价于一段效应上下文中的普通块，不改变推断规则。
- 第一版实现可将 `effect` 关键字 **延后**；语义以「`main` + 推断」为准。用户不可依赖「必须写 `effect` 才能编译」。

### 2.3 求值语义

- Lumia 采用 **严格求值（call-by-value）**。
- 函数参数在传入前完全求值。
- `val` / `var` 绑定在右侧表达式求值完成后绑定。
- `match`、`if` 的分支选择遵循严格语义：被选分支求值，未选分支不求值。
- **例外**：内置短路运算符 `and`、`or`（以及一元 `not`）按操作数顺序短路，这是语言明确定义的可观测行为。不使用 `&&` / `||` / `!`。

### 2.4 错误语义

- **运行时错误**（越界、除零、模式匹配失败、`assert` 失败）在触发的求值点 **立即** 抛出，不可被编译器静默消除。
- 编译器可证明 **永不触发** 的错误路径（如常量折叠后越界不可能），方可静态报错或优化掉该路径。
- 无 **未定义行为**；所有非法操作或有定义的错误结果，或有定义的陷阱（trap）并附带栈追踪。

### 2.5 用户 **不可** 依赖的实现细节

下列行为 **不是** 语义的一部分；编译器与运行时可任意改变：


| 非语义属性              | 说明                          |
| ------------------ | --------------------------- |
| 堆分配次数与大小           | 中间 `100` 元素序列可能零分配          |
| 子表达式求值次数           | `f(x)` 在纯上下文中可只求值一次         |
| 数据结构的物理表示          | `List` 可能是 range / 融合管道 / 堆块；`Map`/`Set` 可能是小表 / 关联列表 / 哈希 / 有序树 / overlay |
| 复制 vs 原地更新         | 局部 `var` 换绑可能在栈上原地改，也可能 COW |
| 并行度                | 纯计算可自动并行化，只要不影响值与效应顺序       |
| 内联与 specialization | 任意进行，不改变可观测结果               |
| 透明 Memo 是否命中       | 有界缓存可驱逐；命中与否不改变纯函数返回值       |


### 2.6 Debug 与 Release

- **Release 模式**：全力优化，行为符合上述契约。
- **Debug 模式**：降低融合与重排 aggressiveness，效应与求值顺序 **尽量** 贴近源码，便于断点；**值的相等性** 与 **效应顺序** 仍必须与 Release 一致。

## 3. 类型系统

### 3.1 设计原则 —— 完全类型推断

- **静态强类型**，但用户日常 **零注解**。
- 推断算法：全程序 **Hindley-Milner + let-polymorphism + 类型类约束求解**。
- 函数参数、返回值、`val`/`var`、闭包捕获、泛型、ADT 变体 —— **全部推断**。
- 类型注解是 **可选逃生舱**，几乎永远不写；实在要写形如 `**名字: 类型`**：

```lumia
val x: Int = 1
val add = { a: Int, b: Int ->
    a + b
}
```

- **禁止** 把“必须写类型”作为常规编程模型；标准库文档示例一律无注解。
- **无 null**；可选值用 `Option`。
- **无隐式转换**；转换必须显式调用或经类型类解析。
- **代数数据类型（ADT）** 是一等公民；无类继承。

### 3.2 推断失败时的用户体验

- 错误信息用 **具体值与期望** 说话，不要求用户理解 unification 术语。
- 例：`这里是 String，但 + 需要数字`；`这个函数被用成了两个不同参数类型`。
- IDE / LSP 可悬停显示推断结果；**源码里不强制出现**。

### 3.3 基本类型（编译器内部；用户通常不写）

```
Int, Int8, Int16, Int32, Int64
UInt, UInt8, ...
Float32, Float64
Bool, Char, String, Unit
```

- `Int` 为平台字长或有界语义（实现阶段定，文档层假设 64-bit）。
- `String` 为 UTF-8 不可变文本；内部实现可变宽优化，对用户不可见。
- 数字字面量默认推断为 `Int` / `Float64`；过载由类型类与使用上下文消歧。

### 3.4 复合类型

```
Option[T]          // Some(v) | None
Result[T, E]       // Ok(v) | Err(e)
List[T]            // 统一序列类型，用户无其他变体
Map[K, V]          // 统一映射类型，用户无 HashMap/TreeMap 分型
Set[T]             // 统一集合类型，用户无 HashSet/TreeSet 分型
Tuple[T1, T2, ...]
Nominal product / sum   // 由 `type` 声明；见 §4.7
Fn[A, B, ...]           // 一等函数（多参）
```

### 3.5 列表类型 `List` —— 单一用户视图

用户对 `List` 只感知下列操作：

```lumia
listOf()                   // 空列表（正规构造）
listOf(1, 2, 3)
[]                          // 糖 → listOf()
[1, 2, 3]                   // 糖 → listOf(1, 2, 3)
range(1, 100)               // 半开区间 [1, 100)（正规）
rangeInclusive(1, 100)      // 闭区间 [1, 100]（正规）
1..<100                     // 糖 → range(1, 100)
1..100                      // 糖 → rangeInclusive(1, 100)
xs.concat(ys)               // 连接（无 ++ 运算符）
xs[i]                       // 糖 → xs.get(i)；越界 trap（与既有 List 语义一致）
xs.len()
xs.map(f).filter(p).fold(z, op)   // 管道 map ≠ 类型 Map；≠ mapOf
for x in xs { ... }

xs match {
    [] -> None
    [x, ..rest] -> Some(x)
}
```

**关键设计**：不存在 `Stream`、`Array`、`Vector`、`Range` 等用户可见分型。  
编译器内部对 `List` 使用 **多重表示（multi-representation）**：

```
LitList      // 常量折叠
Iota         // start..end / range
Fused        // map/filter 融合视图
Slice        // 子视图
HeapList     // 物化堆数组
COWList      // 写时复制缓冲
```

表示之间的转换由 **逃逸分析** 与 **使用模式分析** 自动插入，用户无感。  
选择纪律见 **§7.1.1**：分析能证明时才离开默认路径。  
构造与糖的统一规则见 **§3.5.2**。

### 3.5.1 映射与集合 `Map` / `Set` —— 与 `List` 同一哲学

`Map` / `Set` **进入语言复合类型**（与 `List` 同级），不是「普通库类型随便写写」。  
理由与 `List` 相同：要做 **单一用户视图 + 多重表示 + 按需物化**，编译器必须认识它们；API 厚实部分仍可落在 `std`，但 **类型与表示选择是语言契约**。

**关键设计**：不存在用户可见的 `HashMap` / `TreeMap` / `LinkedHashMap` / `HashSet` / `TreeSet`。  
用户只写 `Map` / `Set`；物理结构由编译器按键能力与使用模式选择。

#### 用户视图

```lumia
mapOf()                                 // 空 Map（正规构造）
mapOf("a" to 1, "b" to 2)               // 首选：中缀 to
mapOf(("a", 1), ("b", 2))               // 等价：显式元组
[:]                                     // 糖 → mapOf()
["a" : 1, "b" : 2]                      // 糖 → mapOf("a" to 1, "b" to 2)

setOf()                            // 空 Set
setOf(1, 2, 3)
#{}                                 // 糖 → setOf()
#{1, 2, 3}                          // 糖 → setOf(1, 2, 3)

m[k]                        // 糖 → m.get(k)：Option[V]（缺键为 None，不 trap）
m.get(k)
m.contains(k)
m.set(k, v)                 // 新 Map；同键覆盖（更新，不是 mapOf）
m.remove(k)
m.len()
m.keys()                    // List[K]（插入序）
m.values()
m.items()                   // List[(K, V)]

s.contains(x)
s.insert(x)
s.remove(x)
s.union(t) / s.intersect(t) / s.diff(t)
s.len()

for (k, v) in m { ... }
for x in s { ... }
```

- 更新一律 **值语义**：`m = m.set(k, v)`，无原地 `m[k] = v` 赋值语法。
- `List` ↔ `Map`：`pairs.toMap()`、`m.items()`；重复键时 **后者覆盖**。
- `List` ↔ `Set`：`xs.toSet()`、`s.toList()`；重复元素去重。
- 第一版 **不做** `Map`/`Set` 的深度 `match` 拆解；用 `get` / `contains` / `items`。
- **命名**：管道 `xs.map(f)` ≠ 类型 `Map` ≠ 构造 `mapOf`（学 Kotlin：`map` / `Map` / `mapOf`）。

### 3.5.2 正规构造与语法糖（学 Kotlin `listOf` / `mapOf`）

**原则**：集合的 **语义入口是函数**；便捷写法是糖，desugar 之后与手写构造 **同一 IR**，优化认的是 `listOf` / `mapOf` / `setOf` / `range` 等已知函数，不是字符形状。  
**命名风格**：标准库与集合 API 使用 **驼峰**（`listOf`、`toMap`、`flatMap`），**不**使用下划线；与 Kotlin 习惯对齐。

| 糖（日常） | 正规形式 |
|------------|----------|
| `[]` / `[a, b, c]` | `listOf()` / `listOf(a, b, c)` |
| `1..<n` / `1..n` | `range(1, n)` / `rangeInclusive(1, n)`（Kotlin 对齐） |
| `[:]` / `[k : v, ...]` | `mapOf()` / `mapOf(k to v, ...)` |
| `#{}` / `#{a, b}` | `setOf()` / `setOf(a, b)` |
| `xs[i]`（List） | `xs.get(i)` |
| `m[k]`（Map） | `m.get(k)` |
| `k to v` | `(k, v)`（中缀；`mapOf` 参数的首选写法） |

`mapOf` 参数：

- **推荐** `mapOf(key to value, ...)` —— 与 Kotlin 相同，读作「键到值」。
- 亦接受 `mapOf((key, value), ...)`；与 `to` 语义相同（都是 `(K, V)`）。
- 重复键：**后者覆盖**。
- `to` 是普通中缀函数（或内建糖），优先级低于调用实参逗号分隔；不引入新的映射类型。

**编译器**：对上述正规函数做表示选择与融合（§7.1.1）；糖不增加第二种语义。  
**模式**中的 `[]` / `[x, ..rest]` 仍是模式语法，不是表达式糖（与 Kotlin 解构类似，保留便捷）。

#### 键 / 元素约束（用户通常不写）

| 需求 | 约束 | 说明 |
|------|------|------|
| 能放进 `Map`/`Set` | 键 / 元素具备 `Eq` | 否则无法定义查找与 `==` |
| 哈希表表示 | 另需 `Hash`（可自动派生） | 用户 **不** 因「要用 Map」手写 `HashMap` |
| 有序树表示 | 另需 `Ord` | 仅当编译器认为树更优时选用 |

`Hash` 与 `Show` / `Eq` / `Ord` 一样是能力：标量与由它们构成的积/和 **可自动派生**；用户几乎不写。  
缺 `Hash`、仅有 `Eq` 时，仍可使用 `Map`/`Set`——编译器退到小表 / 关联列表等表示，语义不变。

#### 可观测语义（必须钉死）

| 问题 | 决议 |
|------|------|
| `m1 == m2` | **按键值内容** 结构相等；与插入顺序无关 |
| `for` / `items` / `keys` 顺序 | **插入序**（同键 `set` 覆盖 **不** 改变该键已有位置；`remove` 后再 `set` 视为新插入到末尾） |
| 缺键 `m[k]` | `None`，不是 trap |
| 物理表示、是否已建哈希表、overlay 层数 | **非语义**（§2.5） |

插入序可观测（效应循环会打印顺序），因此 Debug / Release **必须** 一致；表示选择不得改序。

#### 编译器多重表示（用户无感）

```
EmptyMap / EmptySet     // 空
LitMap / LitSet         // 常量折叠
SmallMap / SmallSet     // 内联 ≤ N 对/元（线性；N 实现自定，典型 4～8）
AssocList               // 未建索引的配对列表（构建中、或仅 Eq）
Overlay                 // 父结构 + 小差分（COW 更新）
HashOrdered             // 插入序哈希（默认大表路径）
SortedTree              // 仅当 Ord 可用且分析认为更优（如大量按键有序扫描）
BuildFused              // 从 List 管道 / fold 构建的延迟视图
```

`Set` 在实现上可共享 `Map[T, Unit]` 引擎，但 **用户类型仍是 `Set[T]`**（API 与错误信息更清楚）。

**默认稳定路径（分析不确定时必须走）：**

| 类型 | 默认 |
|------|------|
| `Map` | `HashOrdered` + COW / `Overlay`（插入序哈希；写时按共享决定拷贝或差分） |
| `Set` | 同上引擎 |
| 字面量很小且未逃逸 | 可直接 `SmallMap`/`SmallSet`（尺寸常量可见 ⇒ 算「能证」） |

`AssocList` / `BuildFused` / `SortedTree` 等 **仅当分析能证明更优或等价且更省** 时启用（§7.1.1）；禁止靠弱启发在默认与特化之间来回赌。

表示转换由 **逃逸分析**、**使用模式** 与 **键能力**（`Hash`/`Ord`）共同决定，并服从 §7.1.1。

#### 按需物化与部分构建

`Map` / `Set` **支持部分构建**，但含义与 `List` 的「只算下标 100」不完全相同。

**支持（实现可做，用户无感）：**

| 模式 | 例子 | 实现可不做什么 |
|------|------|----------------|
| 推迟索引 | `pairs.toMap()` 后只 `get` 几次 | 不建哈希表 / 有序树，留在 `AssocList` / `BuildFused` |
| 查询短路 | `big.toSet().contains(x)` | 扫到命中即可返回；未逃逸时可 **不** 建完整集合索引 |
| 单键探查 | `pairs.toMap().get(k)` | 在融合管道上扫到键 `k`（或穷尽）即得答案，**不必**先物化全部键值对到堆表 |
| 差分更新 | 多次 `set` / `insert` | `Overlay` / 小表；而非每次拷整表 |
| 管道融合 | `.map(...).filter(...).toMap()` | 与 `List` 融合合流，按消费方式再物化 |

```lumia
val m = pairs.toMap()
val v = m.get("only")
```

- **语义**：与先建完整映射再查找相同（含重复键覆盖规则）。
- **实现**：若 `m` 不逃逸且只有少数 `get`，可在 `AssocList` / `BuildFused` 上查找或短路扫描，**永不建全量哈希表**；若逃逸或查找密集，再升为 `HashOrdered` 或 `SmallMap`。

```lumia
var m = [:]
m = m.set("a", 1)
m = m.set("b", 2)
println(m.get("a"))
```

- **实现**：可为 `Overlay` 链或直接 `SmallMap`；逃逸后再压成紧凑表示。

```lumia
val m = lines
    .map(parsePair)
    .filter(valid)
    .toMap()
```

- **实现**：`BuildFused`——融合 `map`/`filter`，按消费方式物化；若随后只 `get` 一两次，可能跳过全量哈希。

**不支持（会破坏语义，故不做）：**

- 对外仍是「完整 `Map`/`Set`」值，却在内容上永久残缺（例如只留下用过的键），同时还能对任意键做正确的 `==` / `items` / `len`。
- 用户可见的「惰性 Map 类型」或 `partialMap` API。

**边界一句话**：部分构建省的是 **索引与中间堆表**；一旦可观测地需要全集信息（`==`、`len`、`items`、逃逸后的完整值），必须能得到与「先完整构建」相同的结果——此时再补建，而不是交残缺值。

#### 明确拒绝

- 用户可选 `HashMap` vs `TreeMap`
- 依赖哈希迭代乱序
- `capacity` / 负载因子等实现 API
- 以引用同一性为键（无 `Ref`，键只能是值）


`trait` 的意思是：**某类值具备的能力**（能打印、能比较、能加减……）。

日常编程里你 **几乎不写** `trait`：直接写 `a == b`、`a < b`、`a + b`，编译器自动找对应能力。  
只有给 **自己定义的类型** 规定「怎么比较 / 怎么显示」时，才需要碰它。

用人话对照：


| 能力名    | 人话          | 你平时怎么用到               |
| ------ | ----------- | --------------------- |
| `Show` | 能变成文字       | `println(x)`、`"${x}"` |
| `Eq`   | 能判断相等       | `a == b`；`Map`/`Set` 的键 |
| `Hash` | 能稳定散列       | 几乎不直接写；供 `Map`/`Set` 选哈希表示 |
| `Ord`  | 能比大小（先要能判等） | `a < b`、排序；亦可供有序树表示 |
| `Num`  | 能当数字算       | `a + b`、`a * b`       |


完整写法示例（标准库内部风格；用户可选阅读）：

```lumia
// 「能显示成字符串」
trait Show {
    val show = { self ->
        // 返回 String
    }
}

// 「能判断两个值是否相等」
trait Eq {
    val eq = { self, other ->
        // 返回 Bool
    }
}

// 「能散列」—— Map/Set 选哈希表示时用；标量与由 Hash 字段构成的类型可自动派生
trait Hash {
    val hash = { self ->
        // 返回 Int（或实现定义的散列宽）
    }
}

// 「能比大小」—— 前提是已经能判等（所以写 requires Eq）
trait Ord requires Eq {
    val less = { self, other ->
        // 返回 Bool：self < other ?
    }
}

// 「能做算术」
trait Num {
    val add = { self, other ->
        // self + other
    }
    val mul = { self, other ->
        // self * other
    }
}
```

- `requires Eq` 的意思：**要会排序，必须先会判等**——不是继承，是前提条件。
- 给自己的类型加能力时用 `instance`（见标准库文档）；**约束由编译器自动推导**，用户不写注解、不写字典参数。
- 若暂时不需要自定义比较/显示，可完全忽略本节。

### 3.7 效应类型（对用户隐藏）

内部 IR 携带 **效应集合** `ε`：

```
val f : Fn[A] -> B / ε
```

- 用户 **不写** 效应注解，也 **不强制** 写 `effect { }`；编译器 **推断**。
- 纯函数 `ε = ∅`；含 `println` 的函数 `ε ⊇ IO`。
- 纯函数可在纯表达式中调用；效应函数只能在 **效应上下文** 中调用（`main`、有效应函数体、可选的 `effect` 块）。
- `main` 由运行时在效应根中调用；即使体为空也视为效应入口。
- 高级用户可选 `--show-effects` 调试，不是语言核心语法。

#### 3.7.1 推断与传播

- 效应沿调用图 **静态传递**：若 `F` 直接执行效应，或调用（含间接）任一有效应函数，则 `F` 的 `ε` 非空。
- 判定依据是「调用图上是否 **可达** 效应」，不是某次运行是否走到那条路径。
- 因此从效应叶子到根路径上的函数，边界上都会带效应标签；根通常是 `main`。

#### 3.7.2 函数边界 vs 函数体内纯区域

函数级 `ε` 是 **边界标签**；体内粒度更细。

```lumia
val mixed = {
    // 前段：纯计算（IR 中为纯区域）
    val a = heavy_pure(xs)
    val b = a.map(f).filter(p)

    // 效应语句：可观测副作用的最小单位（无需包 effect）
    println(b[0])

    // 后段：仍可为纯区域
    b.len
}
```

- `mixed` 的 `ε` 非空：不能从纯表达式调用，不能对 **整函数** 做透明 Memo（§7.5.4）；可从 `main` 或其他效应函数调用。
- `heavy_pure` / `map` / `filter` / `len` 等无效应子计算：纯分析后可做 CSE、融合、DCE、局部消重等（§7.2、§7.5.1-A）。
- 编译器 **不保证** 把前段/后段自动 outline 成用户可见的独立纯函数；需要跨调用复用或在纯上下文调用时，用户应自行拆出纯函数：

```lumia
val compute = { xs -> xs.map(f).filter(p) }   // ε = ∅

val report = {
    println(compute(data))   // report 因 println 推断为有效应；无 effect 包裹
}

val main = {
    report()
}
```

- **推荐**：把「算值」与「做效应」分开；不必把任意语句都拆成函数，也 **不必** 为效应包 `effect { }`。体内纯区域已可优化；拆函数是为了 **边界纯度** 与 **跨调用 Memo**，不是为了启用基本优化。

### 4.0 注释与字符串

```lumia
// 单行注释

/* 多行
   注释 */

val s = "hello ${name}"   // 块插值
val t = "hello $name"     // 简单标识符插值
```

- 插值是 **纯** 的（只做格式化，不触发 I/O）。
- 注释：`//` 单行，`/* */` 多行。

---


| 关键字   | 含义                        | 允许位置             |
| ----- | ------------------------- | ---------------- |
| `val` | 不可换绑；绑定一次                 | 模块顶层、块内、参数引入的命名；块内亦可不可反驳模式：`val (a, b) = p`、`val Point { x, y } = p`（变体/列表/常量请用 `match`） |
| `var` | **可换绑**（rebind）；同一名字可再次赋值 | **仅局部块内**；禁止模块顶层 |


**决定：支持 `var`。**

理由（不妥协）：

1. “写像命令”需要循环累加、状态机步进等顺序心智；没有换绑会逼用户写嵌套递归或手动 `fold`，增加心智负担。
2. `var` 只是 **换绑**，不是共享可变内存；语义上每次赋值是新值贴上旧名字，编译器降为 **SSA**。
3. 与 `val` 成对，心智模型极简：`val` 定了就定了，`var` 可以改指。
4. **不提供** 共享可变单元（无 `Ref` / 无指针别名）；见 §6。

规则：

- 模块顶层 **只有 `val`**（含函数定义）。
- `var x = ...` 之后 `x = ...` 合法；对 `val` 赋值是编译错误。
- 闭包捕获 `var`：**按创建闭包时的当前值捕获**（拷贝语义）。需要“之后还能改外面那个名字”时，把状态留在外层块里换绑，或让函数 **返回新值** 由调用方写回。
- `var` 换绑 **不是 I/O 效应**；纯块内允许 `var`（编译器 SSA 化后仍可证明纯度）。
- 对 `List` 的“改元素”仍用值语义：`xs = xs.set(i, v)`。

```lumia
val add = { a, b ->
    a + b
}

var n = 0
n = n + 1
```

```lumia
module MyApp

import std.io.{println}

val square = { x ->

val main = {

```

### 4.3 表达式 vs 语句


| 类别  | 形式                                   | 说明 |
| --- | ------------------------------------ | --- |
| 表达式 | `val`/`var` 绑定、`if`、`match`、调用、字面量、块 | 纯块有值；**最后一行是返回值** |
| 语句  | `println(...)`、`var` 赋值              | 效应上下文或块内顺序步骤 |
| 效应块 | `effect { ... }`（**可选**）              | 显式隔离；语义等同普通块（§2.2.1） |


**有限 `return`**：`return expr` 从**最近一层函数/闭包**早退（无 Kotlin 非局部返回）；块的值仍可由最后一行给出。循环内提前结束用 `break`/`continue`。

### 4.4 函数定义 —— 统一为 `val` + 块

函数 **没有** 独立的 `fn` 关键字。函数就是绑定到名字上的块（一等值）。

#### 形式 A：参数写在名字后（推荐 / 标准库写法）

```lumia
val add(a, b) = {
    a + b
}
```

- 参数在左侧，块内 **不再** 写 `{ a, b ->`。
- 函数体相对 `{` **缩进 4 个空格**（`lumia fmt` 强制；禁止 Tab）。
- **最后一行表达式** 为返回值；亦可用有限 `return expr`（见 §4.3、§8）。
- 参数、返回类型 **完全推断**。
- **`std/` 标准库**一律用此形式。

单行 / 无花括号短形式：

```lumia
val add(a, b) = { a + b }
val add(a, b) = a + b
```

- **顶层零参**：`val name() = { ... }`，或省略括号的 `val name = { ... }`（块内无 `->`，也不是 `{ -> ... }`）等价。例如：

```lumia
val answer() = { return 42 }
val report = {
    println("hi")
}
// 调用：answer() / report()
```

- 显式零参箭头 `{ -> body }` 与上式在**顶层**等价；在**局部**绑定里则不同：`val y = { … }` 是立刻求值的作用域块，局部零参闭包须写 `{ -> … }`（或 `val y() = { … }`）。

#### 形式 B：参数写在块头（可选，多用于局部闭包）

```lumia
val add = { a, b ->
    a + b
}
```

- 与形式 A **语义完全等价**；有参数时必须写 `{ 参数列表 ->`，`->` 不可省略（单参短闭包用 `it` 时可省略参数列表，见下）。
- 适合内联 / 一等闭包字面量；顶层命名函数优先形式 A。

单行形式：

```lumia
val add = { a, b -> a + b }
```

#### 匿名函数 / 高阶

```lumia
// 完整写法：闭包作为普通参数
val ys = xs.map({ x ->
    x * x
})

val ys2 = xs.map({ x -> x * x })
```

#### 尾随闭包（trailing closure）

若函数的 **最后一个参数是函数**，允许把该闭包写在 **调用括号外面**（Kotlin / Swift 同款）：

```lumia
// 推荐：尾随闭包
val ys = xs.map { x ->
    x * x
}

// 前面还有普通参数时：括号里放前面的，闭包拖在后面
val sum = xs.fold(0) { acc, x ->
    acc + x
}

xs.filter { y ->
    y > 100
}

// 无参闭包也可以尾随
run {
    println("hi")
}
```

规则：


| 规则     | 说明                                      |
| ------ | --------------------------------------- |
| 适用     | **仅最后一个** 参数是函数类型时                      |
| 括号     | 若没有其它参数，可省略 `()`：`xs.map { ... }`       |
| 有其它参数  | 写成 `f(a, b) { ... }`，闭包对应最后一个形参         |
| 语义     | 与 `f(a, b, { ... })` **完全等价**，只是语法糖     |
| 多个函数参数 | 只有 **最后一个** 可尾随；其余仍写在括号内                |
| 链式     | 每环都可以尾随：`xs.map { ... }.filter { ... }` |


```lumia
// 等价三组
xs.map({ x -> x * x })
xs.map { x -> x * x }

xs.fold(0, { acc, x -> acc + x })
xs.fold(0) { acc, x -> acc + x }
```

官方风格（`lumia fmt`）：**最后一个参数是闭包时，优先写成尾随形式。**

#### 短闭包：单参可用 `it`（Kotlin 式）

闭包 **恰好一个参数** 时，可省略参数列表，用隐式名字 `**it`**：

```lumia
xs.map { it * it }
xs.filter { it > 100 }
xs >> map { it.toLower() }
```

规则：


| 规则    | 说明                                   |
| ----- | ------------------------------------ |
| 适用    | 仅 **单参数** 闭包                         |
| 多参数   | 必须写出名字：`{ a, b -> a + b }`，无 `it`    |
| 与显式参数 | `{ x -> x * x }` 仍合法；与 `it` 二选一，不能混用 |
| 官方风格  | 单参短体优先 `it`；复杂体可显式命名                 |


**与 `match` 无冲突**：`match` 是 **中缀**。优先级：**先 `>>`，再 `match`**：

```lumia
findIndex(xs) { it > 0 } match {
    Some(i) -> i
    None -> -1
}

xs.map { it * 2 }.filter { it > 10 } match {
    [] -> 0
    [h, ..] -> h
}

// 管道再 match
xs >> filter { it > 0 } match {
    [] -> None
    [h, ..] -> Some(h)
}
```

#### 管道符 `>>`

数据从左流向右，送入下一个函数（学 Elixir/`|>` 的语义，**符号定为 `>>`**）：

```lumia
// x >> f          等于  f(x)
// x >> f >> g     等于  g(f(x))

val result = raw
    >> trim
    >> split(' ')
    >> filter { w -> w.len() > 0 }
    >> map { w -> w.toLower() }
```

规则：


| 规则        | 说明                                                                     |
| --------- | ---------------------------------------------------------------------- |
| 语义        | `x >> f` ≡ `f(x)`；左结合：`a >> b >> c` ≡ `(a >> b) >> c`                  |
| 多参数       | **左侧是第一个参数**：`xs >> map { x -> x * 2 }` ≡ `map(xs) { x -> x * 2 }`     |
| 与 `.`     | `.` 偏方法/UFCS 链式；`>>` 偏自由函数管道；二者可混用                                     |
| 与尾随       | 管道右侧可以是「调用 + 尾随闭包」：`xs >> filter { it > 0 }`                           |
| 与 `match` | `**>>` 优先于 `match`**：`x >> f match { ... }` ≡ `(x >> f) match { ... }` |


```lumia
// 三种等价风格（官方不强制唯一）
xs.map { x -> x * 2 }.filter { y -> y > 10 }

xs
    >> map { x -> x * 2 }
    >> filter { y -> y > 10 }

map(xs) { x -> x * 2 }.filter { y -> y > 10 }
```

**位运算**：语言 **不** 用 `>>` / `<<` 做移位；若需要移位，用函数名（如 `shiftRight` / `shr`），避免与管道冲突。

#### 递归

同模块内 `val` 可相互递归；编译器做递归绑定组分析：

```lumia
val fib(n) = {
    n match {
        0 -> 0
        1 -> 1
        _ -> fib(n - 1) + fib(n - 2)
    }
}
```

- 函数是一等值；闭包捕获遵循 **最小捕获 + 逃逸分析**。
- 尾调用：纯相互递归 **保证** TCO；含 I/O 效应的不保证。

#### 箭头 `->` 的两处用途


| 位置                | 含义                                              |
| ----------------- | ----------------------------------------------- |
| `{ a, b -> ... }` | 参数列表结束，函数体开始                                    |
| `模式 -> 表达式` / `模式 -> { 块 }` | `match` 臂（单表达式可省略 `{}`；多语句用块；守卫：`pattern if cond -> ...`） |


语言中 **不使用** `=>`。

### 4.5 `if` / `else if` / `else`

`if` 是 **表达式**：选中的分支求值，其余不求值；分支体是块，**最后一行是该分支的值**。

#### 基本形式

```lumia
if cond {
    ...
} else if cond2 {
    ...
} else {
    ...
}
```

- 条件必须是 `Bool`。
- **大括号必写**（禁止悬空 `else`、禁止单行无括号）。
- 多分支用 `**else if` 链**（不引入 `elif` / `when`）。
- 布尔多路分支用 `if`；按值/形状分派用 `match`（§4.7），不另造 `switch`/`when`。

#### 作为值使用

```lumia
val max = if a > b { a } else { b }

val grade = if score >= 90 {
    "A"
} else if score >= 80 {
    "B"
} else if score >= 60 {
    "C"
} else {
    "D"
}

val abs = { x ->
    if x < 0 { -x } else { x }
}
```

规则：


| 情况                              | 要求                                   |
| ------------------------------- | ------------------------------------ |
| `if` 的结果被当作值用（赋给 `val`、作为最后一行等） | 必须有 `else`（或等价穷尽），且各分支类型一致（可推断出公共类型） |
| `if` 只做效应 / 只改 `var`，结果丢掉       | `else` 可省略；类型为 `Unit`                |


```lumia
// 合法：当语句用，无 else
if ready {
    println("go")
}

// 合法：改 var
var r = x
if x < 0 {
    r = -x
}

// 非法：当值用却无 else
val y = if x > 0 { x }    // 错误：缺 else
```

#### 与 `match` 怎么选


| 你在分什么          | 用                                         |
| -------------- | ----------------------------------------- |
| 真 / 假，或若干布尔条件  | `if` / `else if`，或无主体 `match { cond -> … }` |
| 枚举变体、结构形状、常量模式 | 中缀 `expr match { pattern -> … }`                                   |
| 先拆开再带条件        | 中缀 `match` + 守卫 `pattern if cond -> ...` |


```lumia
// 布尔多路 —— 无主体 match（学 Kotlin when { }）
val msg = match {
    n == 0 -> "zero"
    n == 1 -> "one"
    _ -> "many"
}

// 同一值多种形状 —— 中缀 match
val msg2 = n match {
    0 -> "zero"
    1 -> "one"
    _ -> "many"
}
```

两种都合法；形状/穷尽检查用中缀 `match`；布尔条件链更宜无主体 `match { }`。

#### 不支持的写法

```lumia
if (cond) stmt;           // 无括号条件也可以，但分支必须是块
if cond then a else b     // 不使用 then
cond ? a : b              // 不使用三元；用 if 表达式
```

#### 运算符（逻辑与算术）


| 类别          | 写法                                            |
| ----------- | --------------------------------------------- |
| 逻辑与 / 或 / 非 | `**and**` / `**or**` / `**not**`（短路；不用 `&&` ` |
| 比较          | `==` `!=` `<` `<=` `>` `>=`                   |
| 算术          | `+` `-` `*` `/` `%`                           |
| 管道          | `>>`                                          |
| 按位与 / 或     | **不用符号**；需要时用函数名（如 `bitAnd` / `bitOr`）      |
| 移位          | 不用 `<<` `>>`；`>>` 专属管道；移位用函数名                 |


```lumia
if x > 0 and not done {
    ...
}
if a or b {
    ...
}
```

### 4.6 块语义：最后一行返回

```lumia
val abs(x) = {
    var r = x
    if x < 0 {
        r = -x
    }
    r          // 最后一行：返回值
}
```

- 块内可有多个 `val`/`var`、`if`、`match`、`for`。
- **最后一个表达式** 的值是块的结果；类型即该表达式的类型。
- 若块在效应上下文且最后需要无值，结果为 `Unit`（可省略显式 `()`）。

### 4.7 模式匹配：`expr match { }` 与无主体 `match { }`

#### 中缀（学 Scala）：按值 / 形状

`match` 作 **中缀**：先写被匹配的值，再写 `match { 臂 }`。`match` 须与主体 **同一行**（换行后的 `match {` 是无主体形式）。

```lumia
expr match {
    pattern -> expr
    pattern if guard -> expr
    pattern -> {
        // 多语句时用块；最后一行是该臂的值
        ...
    }
    _ -> expr
}
```

#### 无主体（学 Kotlin `when { }`）：布尔多路

```lumia
match {
    n > 0 -> "pos"
    n == 0 -> "zero"
    _ -> "neg"
}
```

- 臂为 **`条件 -> 体`**；条件是布尔表达式。
- 兜底臂 **`_ -> …` 必须有且放最后**（表达式用途；对齐 Kotlin 的 `else`）。
- 自上而下求值条件；第一个为真的臂求值；只求值选中臂。
- 语义上等价于嵌套 `if` / `else`。

#### 中缀规则摘要

- 形态：`**表达式 match { 臂... }**`；不是前缀 `match 表达式 { }`。
- 匹配 **必须穷尽**；编译器静态检查。
- 臂语法：`**模式 [if 守卫] -> 表达式`** 或 `**模式 [if 守卫] -> { 块 }`**。
- **或模式**：同一臂多个模式用 **逗号** 隔开（匹配任一即可）：

```lumia
n match {
    0, 1 -> "small"
    _ -> "big"
}

opt match {
    None, Some(0) -> "empty-ish"
    Some(n) -> "${n}"
}
```

- 臂体可以是 **单个表达式**（无需 `{}`），也可以是 **`{ }` 块**（多语句、局部绑定）。
- 单表达式臂解析为一个完整表达式后结束；下一臂从下一个模式开始。
- 块内 **缩进 4 空格**；块的 **最后一行** 为该臂的值。
- 臂 **从上到下** 尝试；只求值选中臂。
- 守卫：模式成功后再求值 `if`；为 `false` 则试下一臂。
- **不用** `=>`、`when` 关键字；无主体布尔多路用 `match { }`（见上）。
- 与尾随闭包 / 管道：先完成调用与 `>>`，再中缀 `match`（`**>>` 优先于 `match`**）。

#### 完整示例

```lumia
module MatchDemo

import std.io.{println}

type Point {
    val x
    val y
}

type Option {
    Some(value)
    None
}

type Expr {
    Lit(n)
    Add(left, right)
    Mul(left, right)
}

type Cmd {
    Quit
    Run(name)
}

// —— 常量 / 通配 / 绑定 ——
val describe_n = { n ->
    n match {
        0 -> "zero"
        1 -> "one"
        k -> "other: ${k}"
    }
}

// —— 元组 ——
val swap = { pair ->
    pair match {
        (a, b) -> (b, a)
    }
}

// —— 和类型变体 ——
val unwrap_or_zero = { opt ->
    opt match {
        None -> 0
        Some(n) -> n
    }
}

// —— 积类型拆开 + 字段约束 ——
val point_label = { p ->
    p match {
        Point { x, y = 0 } -> "on x-axis, x=${x}"
        Point { x = 0, y } -> "on y-axis, y=${y}"
        Point { x, y } -> "(${x}, ${y})"
    }
}

// —— 列表：空，或「头一个 + 剩下」——
val list_head = { xs ->
    xs match {
        [] -> None
        [x, ..rest] -> Some(x)   // x = 10；rest = [20, 30]（若 xs 是 [10, 20, 30]）
    }
}

// —— 守卫：模式成功后再看条件 ——
val classify = { opt ->
    opt match {
        Some(n) if n > 100 -> "big"
        Some(n) if n > 0 -> "positive"
        Some(_) -> "non-positive"
        None -> "none"
    }
}

val parity = { n ->
    n match {
        k if k % 2 == 0 -> "even"
        _ -> "odd"
    }
}

val diag_or_sum = { p ->
    p match {
        Point { x, y } if x == y -> "diag"
        Point { x, y } -> x + y
    }
}

// —— 多语句臂（必须用块；最后一行是值）——
val double_sum = { p ->
    p match {
        Point { x, y } -> {
            val s = x + y
            s * 2
        }
    }
}

// —— 嵌套 / 递归结构 ——
val eval = { e ->
    e match {
        Lit(n) -> n
        Add(left, right) -> eval(left) + eval(right)
        Mul(left, right) -> eval(left) * eval(right)
    }
}

// —— 命名载荷变体 ——
val handle = { cmd ->
    cmd match {
        Quit -> "bye"
        Run(name) if name == "demo" -> "run demo"
        Run(name) -> "run ${name}"
    }
}

val main = {
    println(describe_n(0))
    println(describe_n(7))

    println(swap((1, 2)))

    println(unwrap_or_zero(None))
    println(unwrap_or_zero(Some(42)))

    println(point_label(Point { x = 3, y = 0 }))
    println(point_label(Point { x = 1, y = 2 }))

    println(list_head([]))
    println(list_head([10, 20, 30]))

    println(classify(Some(150)))
    println(classify(Some(5)))
    println(parity(4))

    println(diag_or_sum(Point { x = 2, y = 2 }))
    println(double_sum(Point { x = 1, y = 3 }))

    val e = Add(Lit(2), Mul(Lit(3), Lit(4)))
    println(eval(e))

    println(handle(Quit))
    println(handle(Run("demo")))

    // 当语句用：只做效应（单调用也可省略块）
    Quit match {
        Quit -> println("done")
        Run(_) -> println("should not run")
    }
}
```

#### 禁止写法

```lumia
x match {
    when n > 0 -> ...         // 非法：不用 when
}

match x {                     // 非法：不用前缀 match；应为 x match { }
    _ -> 0
}
```

### 4.8 循环：`for { }`，无 `while`

语言 **不提供 `while`**。循环统一用 `**for**` + 块 `{}`。

#### 形式 A：`for x in xs { }` —— 遍历（首选）

```lumia
for i in 1..10 {
    println(i)
}

for x in xs {
    println(x)
}

var acc = 0
for i in 1..n {
    acc = acc + i
}
```

- `in` 右侧必须是可迭代值（`List`、`Map`、`Set`、范围 `1..n` / `1..<n` 等）。
  - `Map` 迭代元素类型为 `(K, V)`；`Set` 为元素本身；顺序见 §3.5.1（插入序）。
- 循环变量 `**i` / `x` 只读**（每轮一个新绑定；不在循环体内赋值 `i`）。
- 需要累加时用外层 `var`。
- 支持 `**break`**（跳出循环）与 `**continue`**（进入下一轮）。

```lumia
for x in xs {
    if x < 0 {
        continue
    }
    if x == 0 {
        break
    }
    println(x)
}
```

#### 形式 B：`for cond { }` —— 条件循环（替代 `while`）

```lumia
var i = 1
var acc = 0
for i <= n {
    acc = acc + i
    i = i + 1
}
```

- `for 布尔条件 { 块 }`：条件为 `true` 则执行块，再重新判断；与旧式 `while` 同语义，**仅换关键词**。
- 条件必须是 `Bool`。
- 能写成范围时 **优先** `for i in ...`，更清晰：

```lumia
// 推荐
for i in 1..n { acc = acc + i }   // 若不需要手动步进

// 条件循环：步进不规则、等待外部状态时
for connected == false {
    retry()
}
```

#### 不支持

```lumia
while cond { ... }     // 无 while
for (i = 0; i < n; i++) // 无 C 风格 for
```

`break` / `continue` **支持**（仅用于 `for`）。无标签 break（0.8 不引入嵌套标签）。

#### `for` 与 `if` / `match` 对照


| 需求        | 写法                |
| --------- | ----------------- |
| 遍历集合 / 范围 | `for x in xs { }`；`for (k, v) in m`（Map→`items`）或已是 `List[(K,V)]` 的列表（如 `m.items()` / `listOf((k,v),…)`） |
| 条件反复执行    | `for cond { }`    |
| 分派一次      | `match` / `if`    |


### 4.9 统一的 `type`：积与和

只用一个关键词 `**type`**。块里写什么，决定是积类型还是和类型——**不靠 `,` / `|`，也不靠 `struct` / `enum`。**

#### 判别规则（对人直觉）


| 块内成员              | 含义            | 角色       |
| ----------------- | ------------- | -------- |
| `val 字段名`         | 这个字段 **一定有**  | 积类型（结构体） |
| `变体名` / `变体名(载荷)` | **多选一** 的一种形状 | 和类型（枚举）  |


- 同一 `type` 块内 **不得混用**：要么全是 `val` 字段，要么全是变体。
- 结构体字段 **只允许 `val`，不允许 `var`**（见下）。
- 枚举变体 **不写** `val`/`var`。

```lumia
// 积：一捆字段 —— 用 val 声明
type Point {
    val x
    val y
}

// 和：多种形状 —— 不用 val/var
type Option {
    Some(value)
    None
}

type Result {
    Ok(value)
    Err(error)
}

type Expr {
    Lit(n)
    Add(left, right)
    Mul(left, right)
}
```

#### 为什么结构体要写 `val`，枚举不用

1. **一眼能分清**：看到 `val` → “都有这些字段”；看不到 → “是这些形状之一”。
2. **和绑定关键词一致**：`val` 表示“定下来的名字”，字段是值的一部分，本来就不可换绑。
3. **枚举变体不是绑定**：`Lit` / `None` 是标签（构造器），不是“这个结构里的一个 val”，所以不写。

#### 为什么字段禁止 `var`

可变留在 **绑定** 上，不留在 **字段** 上：

```lumia
var p = Point { x = 1, y = 2 }
p = p with { x = 3 }          // 换绑整个值 —— 正确
// p.x = 3                   // 禁止：字段级赋值 = 对象可变，已拒绝
```

若允许 `type Point { var x }`，就会回到“改对象内部”，与无 `Ref`、无 class 冲突。

#### 使用语法（声明之后怎么写）

**积类型（有 `val` 字段）**


| 动作   | 语法                        | 例子                                  |
| ---- | ------------------------- | ----------------------------------- |
| 构造   | `类型名 { 字段 = 值, ... }`     | `Point { x = 1, y = 2 }`            |
| 读字段  | `值.字段`                    | `p.x`                               |
| 更新   | `值 with { 字段 = 新值, ... }` | `p with { x = 3 }`                  |
| 换绑更新 | `var` + `with`            | `var p = ...; p = p with { x = 3 }` |
| 拆开   | `match` / `val` 模式        | 见下                                  |
| 比较   | `==`                      | `p == Point { x = 1, y = 2 }`       |


```lumia
type Point {
    val x
    val y
}

val p = Point { x = 1, y = 2 }
val xx = p.x
val yy = p.y

val p2 = p with { x = 10 }              // y 仍为 2
var p3 = p
p3 = p3 with { y = p3.y + 1 }

// 拆开（模式里不再写 val）
val Point { x, y } = p
// 或
p match {
    Point { x, y } -> x + y
}
```

禁止：

```lumia
p.x = 3                       // 字段赋值 —— 非法
Point { val x = 1, val y = 2 }  // 构造时不写 val —— 非法
```

字段绑定一律用 `**=**`（与 `val x = 1` 同形）。`**:` 留给可选类型注解**（如将来 `val x: Int`），不用于字段赋值。

**和类型（变体，无 `val`/`var`）**


| 动作       | 语法                    | 例子                      |
| -------- | --------------------- | ----------------------- |
| 构造（无载荷）  | `变体名`                 | `None`、`Quit`           |
| 构造（位置载荷） | `变体名(值, ...)`         | `Some(42)`、`Add(a, b)`  |
| 构造（命名载荷） | `变体名 { 字段 = 值, ... }` | `Move { x = 1, y = 2 }` |
| 分支       | `match`               | 必须穷尽                    |
| 比较       | `==`                  | `Some(1) == Some(1)`    |


```lumia
type Option {
    Some(value)
    None
}

type Expr {
    Lit(n)
    Add(left, right)
}

type Msg {
    Move { val x, val y }
    Quit
}

val a = None
val b = Some(42)
val e = Add(Lit(1), Lit(2))
val m = Move { x = 1, y = 2 }

b match {
    None -> 0
    Some(n) -> n
}

e match {
    Lit(n) -> n
    Add(l, r) -> eval(l) + eval(r)
}

m match {
    Quit -> 0
    Move { x, y } -> x + y
}
```

禁止：

```lumia
b.value                        // 不经 match 就读变体字段 —— 非法
Some { value = 1 }              // 位置载荷变体不用 {} 构造（除非声明成命名载荷）
```

**对照（同一套语言手感）**

```lumia
// 声明
type Point { val x, val y }     // 有 val → 积
type Option { Some(value), None } // 无 val → 和

// 使用
Point { x = 1, y = 2 }            // 积：类型名 + {}
Some(1)                         // 和：变体名 + ()
p.x                             // 积：直接点字段
o match {
    Some(n) -> n
    None -> 0
}  // 和：先拆开再拿数据
p with { x = 3 }                 // 积：更新
// 和：没有 with 改标签；要变就构造另一个变体
```

#### 语义规则摘要


| 规则   | 说明                                    |
| ---- | ------------------------------------- |
| 相等   | 积：字段皆 `==`；和：同一变体且载荷 `==`             |
| 无身份  | 无“是不是同一个对象”                           |
| 更新   | 仅积类型 `with` / 重新构造；无字段赋值              |
| 名义类型 | `type Point` 与字段同构的 `type Vec2` 是不同类型 |
| 模式   | 拆开时不写 `val`；`val` 只出现在 `type` 声明的字段上  |


变体载荷 **两种都支持**：

```lumia
// 内联积：字段写在变体里（一次性形状）
type Msg {
    Move { val x, val y }
    Quit
}

// 具名积：先 type，再塞进变体（可复用）
type Point {
    val x
    val y
}

type Msg2 {
    Move(Point)
    Quit
}
```

使用：

```lumia
val a = Move { x = 1, y = 2 }
val b = Move(Point { x = 1, y = 2 })

a match {
    Move { x, y } -> x + y
    Quit -> 0
}

b match {
    Move(p) -> p.x + p.y
    Quit -> 0
}
```

#### 编译器实现（用户无感）

运行时 **没有** 对象头 / vtable / 身份哈希：

```
用户:  Point { val x, val y }
         │
         ▼
   ┌─ 小、未逃逸 ──► 寄存器 / 栈槽（SROA）
   ├─ 中、未逃逸 ──► 栈上连续布局
   ├─ 逃逸 / 返回 ──► 堆块或拆成多返回值
   └─ 大 + with   ──► 可共享未改字段（COW），语义仍是新值
```

和类型实现：标签 + 载荷（小枚举可优化为整数；递归变体由编译器加间接，用户不写 `Box`）。

类型与载荷 **完全推断**；公开库可选注解。

## 5. 求值与内存模型

### 5.1 严格求值顺序

表达式树 **左到右、深度优先** 求值，除非：

- 短路运算符
- `match`/`if` 仅求值选中臂
- 编译器证明重排不改变 **纯子表达式的值结果**（对用户不可见）

### 5.2 闭包与捕获

- 捕获变量按值捕获（严格）：创建闭包时拷贝当前值；之后对外层 `var` 的换绑不影响已捕获副本。
- 实现（当前）：逃逸/一等闭包物化为堆对象 `[fn_ptr][cap…]`（`TYPE_CLOSURE`）；无捕获的一等函数仍可用带标签的函数指针。
- 若不逃逸，编译器以后可 **defunctionalization** 或内联（逃逸分析仍待）。

### 5.3 写时复制（COW）

当 `List` / `Map` / `Set` 或大型值需要 **共享** 且 **可能经 `var` 换绑 / `set` 产生新版本** 时：

- 语义：旧值不变，新绑定得到新值（结构相等意义下符合更新语义）。
- 实现：共享底层缓冲或索引直到一次写入触发复制 / `Overlay`；**不是** 语义的一部分。

### 5.4 栈 vs 堆

- 逃逸分析决定分配位置；用户无 `stackalloc`、无 `Box::new` 作为常规 API。
- 小型 `List` 字面量、短生命周期元组、未逃逸的 `var` 局部 → 栈或寄存器。
- 跨函数返回、捕获进逃逸闭包 → 堆。

## 6. 明确拒绝的特性

### 6.1 不支持 `Ref`（共享可变单元）

早期草案曾考虑 `Ref`。**已删除，不进入语言。**


| 想做的事      | 不用 `Ref` 的写法            |
| --------- | ----------------------- |
| 循环累加      | 局部 `var acc`            |
| 函数改“外部状态” | 返回新值，调用方 `x = f(x)`     |
| 两个步骤共享进度  | 同一外层块里的同一个 `var`        |
| 回调里更新     | 回调返回 delta / 新状态，由所有者写回 |


```lumia
val bump = { n ->
    n + 1
}

val main = {
    var counter = 0
    counter = bump(counter)
    println(counter)
}
```

拒绝理由：双轨心智（`var` vs 别名）、击穿逃逸分析与 CSE、引入引用语义、与值相等冲突。  
并发用消息传递；FFI 关在 `unsafe extern`。

### 6.2 不支持类与对象

**不进入语言：`class`、继承、`this`/`self` 方法派发、虚表、子类型多态（名义继承）、对象同一性。**

#### 人要“对象”时，真正想要的是什么


| 直觉需求       | Lumia 对应                                            |
| ---------- | --------------------------------------------------- |
| 一捆相关字段     | `type` + `val` 字段（积类型）                              |
| 几种不同形状     | `type` + 变体 + `match`（和类型）                          |
| 同一操作多种类型   | `trait`（类型类，编译期解析）                                  |
| “这个东西会做……” | 模块里的函数：`move(p, dx, dy)` 或 `p.move(dx, dy)` 语法糖（见下） |
| 封装隐藏细节     | 模块 `pub` / 非 `pub`，不是 `private` 字段继承树               |


```lumia
type Point {
    val x
    val y
}

val move = { p, dx, dy ->
    p with { x = p.x + dx, y = p.y + dy }
}

// 可选语法糖：第一个参数可写成接收者形式（仍是普通函数，无对象语义）
val p2 = p.move(1, 2)    // 语法糖，等同 move(p, 1, 2)
```

#### 为什么类会破坏本语言

1. **对象 = 隐式 `Ref`**：经典 OOP 里 `obj.mut()` 改的是共享身份；与已拒绝的引用语义同构。
2. **心智负担**：构造、继承、覆盖、`super`、接口 vs 抽象类、菱形继承——与“用户无感”相反。
3. **优化敌对**：开方法、向下转型、别名对象，使融合与逃逸分析变难。
4. **完全推断更难受**：名义子类型 + 继承会把 HM 推断拖进歧义泥潭；类型类更适合零注解。
5. **扩展方向错误**：OOP 用继承扩行为；FP 用新函数 / 新 `trait` instance 扩行为，数据用 ADT 扩变体——两套哲学不要混装。

#### 允许的“点调用”（UFCS）—— **要**

- `xs.map(f)`、`p.move(1, 2)` 是 **统一函数调用语法**：第一个参数写到点左边。
- 语义仍是普通函数：`p.move(1, 2)` ≡ `move(p, 1, 2)`。
- 无隐藏 `this` 可变状态；无动态派发（默认）。

#### 和 Kotlin 的边界

Kotlin 的 class 舒服，是因为 JVM 生态与可变对象模型。  
Lumia 取的是 Kotlin 的 `**val`/`var`、块、推断、集合管道**，不取 **class 继承体系**。

## 7. 编译器优化架构

优化是 Lumia **语言设计的一部分**，不是事后附加。

### 7.1 编译流水线

```
Source
  → AST + 效应推断 + 类型检查
  → Core IR（ANF / SSA）
  → 纯分析（逃逸、效应、别名、常量）
  → 优化 Pass 管道
  → Lowering（表示选择；纪律见 §7.1.1）
  → LLVM / 原生代码 / VM bytecode
```

### 7.1.1 表示选择纪律 —— 能证则特化，否则默认

针对「编译期很难次次选对、性能又不宜乱飘」，Lumia 采用：

> **分析能清楚证明时，由编译器走特化表示；不能证明时，走默认稳定路径。**  
> 不在「可能更快」上赌博。

#### 何谓「能清楚证明」

须是 **可靠分析结论**（或常量可见的平凡事实），例如：

- 未逃逸 + 仅一次/常数次下标或 `get` → 可融合 / 短路，不物化全表  
- 范围 `1..n` 且无逃逸消费 → `Iota` / 融合，而非堆数组  
- 字面量或长度上界 ≤ `Small*` 阈值 → 小表  
- 键无 `Hash` 仅有 `Eq` → 不能走哈希默认，改走小表/关联列表（能力缺失是证明，不是猜测）

**不算「能证明」**：模糊热度猜测、跨模块「可能很大」、无证据的「也许该用树」。此类 **必须** 落默认路径。

#### 默认稳定路径（不确定时的唯一主路径）

| 值 | 默认 |
|----|------|
| 逃逸或通用 `List` | `HeapList` / `COWList`（连续缓冲 + COW） |
| 通用 `Map` / `Set` | `HashOrdered` + COW / `Overlay` |
| 透明 Memo | 默认 `T_f` 容量 0 或极小；有证据才增大；硬顶内择优表示（能下标则不下哈希）；见 §7.5 |

默认路径上的 **运行时行为应确定、单调**：

- 扩容、COW 独享检查、小→大升级按固定阈值；  
- **禁止** 同一执行里无意义地降级再升级来回抖；  
- 与 Swift 类似：写时用唯一性/共享决定拷贝，这是默认路径的一部分，不是另一次「表示赌博」。

#### 特化路径（证明后才离开默认）

`Lit*` / `Iota` / `Fused` / `Slice` / `AssocList` / `BuildFused` / `SortedTree` / 栈上 SROA 等：

- 仅当证明 **不劣于默认的可观测语义** 且 **预期资源更省或同样可预期**；  
- Debug 可少做特化，但语义仍与 Release 一致；  
- 启发变更不得改变 §2 可观测合同；性能策略宜 **版本化**，避免静默大跳。

#### 一句话

**证得出 → 编译器定特化；证不出 → 默认（哈希/`COW` 主路径 + 单调升级）。**  
用户仍然零选型；编译器只在有把握时才「聪明」。

### 7.2 核心优化 Pass（Release 默认全开）


| Pass                              | 作用                             |
| --------------------------------- | ------------------------------ |
| **Inline + Specialization**       | 消除小函数、单态化泛型热路径                 |
| **CSE**                           | 纯表达式公共子表达式提一次（局部去重，不是跨调用缓存）    |
| **Transparent Memo**              | 对选中的纯函数挂有界 `T_f` 做跨调用结果复用（用户无语法；见 §7.5）  |
| **DCE**                           | 删除不影响可观测结果的纯计算                 |
| **Escape Analysis**               | 决定栈/堆、是否物化 `List`/`Map`/`Set`        |
| **List Representation Selection** | Lit / Iota / Fused / Heap 自动选择      |
| **Map/Set Representation Selection** | Empty / Lit / Small / Assoc / Overlay / HashOrdered / Sorted / BuildFused |
| **Deforestation / Fusion**        | `map`/`filter`/`fold` 管道融合；含 `toMap`/`toSet` 延迟建索引 |
| **Partial Evaluation**            | 常量索引、常量范围折叠、常量键查找折叠                 |
| **Copy Elimination**              | 未逃逸值避免物理复制                     |
| **Auto Parallelism**              | 纯 `map`/`fold` 在证明无依赖时并行（可选后端） |


### 7.3 融合示例（用户源码 vs 语义）

**用户写：**

```lumia
val ys = (1..1_000_000).map(f).filter(p)
val z = ys[100] + ys[200]
```

**语义：** `z` 的值等于物化列表后取索引。  
**实现：** 可能从未分配百万列表；直接在 range 上融合 `f`、`p`，仅求两个索引位置的值。

**用户写：**

```lumia
var xs = 1..100
xs = xs.set(3, 99)
println(xs[3])
```

**语义：** 第 4 个元素为 99。  
**实现：** 若 `xs` 不逃逸，可能维护小型 overlay + range；若逃逸，物化为 COW heap list。

### 7.3.1 `Map` 按需建索引示例

**用户写：**

```lumia
val m = pairs
    .filter { p ->
        p.1 > 0
    }
    .toMap()
val v = m.get(key)
```

**语义：** 与物化完整 `Map` 后 `get` 相同（含重复键覆盖）。  
**实现：** 不逃逸且单次查找 → 可在过滤后的配对流上线性定位；多次查找或逃逸 → `SmallMap` / `HashOrdered`。

**用户写：**

```lumia
var counts = [:]
for w in words {
    counts = counts.get(w) match {
        Some(n) -> counts.set(w, n + 1)
        None -> counts.set(w, 1)
    }
}
```

**语义：** 插入序计数映射。  
**实现：** 热循环内可走可变槽位的线性探查或本地哈希；一旦 `counts` 逃逸，落成 COW / `HashOrdered`，对外仍是值语义。

### 7.4 优化正确性条件

每个 Pass 必须满足：

1. 保持 `==` 下的值结果。
2. 保持效应语句顺序与可观测 I/O。
3. 保持错误触发点（或静态证明不可达）。

### 7.4.1 有效应函数体内的纯区域

- 纯分析在 **表达式 / 基本块区域** 粒度进行，不因外层函数 `ε ≠ ∅` 而把整段体当作不可优化黑盒。
- 有效应函数体内、不依赖效应的子表达式：允许 CSE、LICM、融合、DCE、局部消重（§7.5.1-A），只要不改变效应语句顺序与可观测 I/O。
- 透明 Memo（有界 `T_f`）仍只挂在 **`ε = ∅` 的函数** 上；体内纯区域不会因此自动获得跨调用 Memo。
- 自动 outline 纯区域为独立函数 **不是** 语义义务；实现可做，用户不可依赖。

### 7.5 透明结果复用

**目标**：用户无感；能快则快；默认内存占用极低；禁止无界全局大哈希表作为默认路径。

**核心合同**：

> 能证明是同一次计算，就算一次；只有跨调用同参复用才经有界 `T_f`；表的有无、表示与容量由代价与硬顶决定；命中不是语义；无用户开关。

#### 7.5.0 优化目标与硬约束

在保持 §2 / §7.4 可观测合同的前提下，Release 对透明复用优化：

```text
Cost = α · CPU + β · PeakMem    （最小化）
```

其中 `α`、`β` > 0 为实现常量（可版本化；改变须记录，避免静默大跳）。`α`/`β` 解释默认倾向（低占用优先），不是用户可调语义。另加硬约束：

| 约束 | 要求 |
| --- | --- |
| 语义 | 不改变纯函数返回值；不改变效应顺序与可观测 I/O |
| 内存 | 每函数条目数上限 + 进程级透明 Memo 总字节上限；满则**驱逐**，禁止无界增长 |
| 负优化护栏 | 未命中路径的额外开销必须有顶；启发失败时不得显著劣于「不建表直接计算」 |
| 单调性 | 同一次执行内，禁止对同一 `T_f` 无意义地扩/缩来回抖（与 §7.1.1 默认路径纪律一致） |
| 用户语法 | **无** `memo` 关键字；用户不可依赖命中、容量、表示 |
| 可观测诊断 | 仅实现开关（如统计计数），不进入语言语义 |

**默认倾向**：`β` 足够大，使「不建表或极小表」优于「大哈希表」；大表仅在代价模型有证据时启用，且仍受硬顶约束。

---

#### 7.5.1 两种手段（勿混为一谈）

透明结果复用只分两类。**禁止**把二者写成同一条「越来越重的梯子」。

##### A. 局部消重（不是跨调用 Memo）

| 手段 | 作用 |
| --- | --- |
| CSE | 同一控制流中重复的纯表达式只保留一次 |
| 内联 + 常量折叠 | 小纯函数在编译期消去 |
| LICM | 循环内不变的纯计算外提 |
| 同指共享 | 证明多处使用同一次纯计算时，只保留一个值（SSA / 外提等）；**无按参数查找** |
| List / Map / Set 融合与表示选择 | 少建中间结构（另一类「省」，见 §7.1～7.3） |

- **零按参查表**；凭「还是不是同一次计算」。
- **做不到**：两个无关调用点都写 `f(1)` 且分析无法共享——那不是 A 的范围，若值得做则走 B。
- 极小函数应在本层解决，**不建** `T_f`。

##### B. 透明 Memo（唯一跨调用机制）

对选中的、整函数效应 `ε = ∅` 的函数 `f`，实现可挂一张**有界**关联表：

```text
T_f : Key(args) → result
```

```text
调用 f(args):
  若 T_f 未启用     → 直接计算
  若 Key(args) 命中 → 返回缓存结果
  否则              → 计算 → 尝试写入（满则按策略驱逐）→ 返回
```

- **用户无语法**；选中与否、命中与否均非语义（§2.5）。
- **默认**多数函数 `T_f` 不存在（容量 0）；只有通过 §7.5.2 才启用。
- 稠密下标、固定小槽、有界开寻址等均为 `T_f` 的**表示与容量参数**，不是多种独立语言机制。

---

#### 7.5.2 建表判据（代价模型）

对候选纯函数 `f`，实现须估计（静态、轮廓或 PGO，允许保守）：

| 符号 | 含义 |
| --- | --- |
| `C_body` | 计算一次体的预期成本 |
| `C_key` | 从 `args` 得到可比较键的成本 |
| `C_lookup` | 一次查找的成本上界（随表示而定） |
| `C_mem` | 为 `T_f` 预留的内存成本（折算进 `β · PeakMem`） |
| `H` | 预期命中率；**无证据时取保守下界** |

**启用 `T_f`（容量 > 0）**：当且仅当预期节省超过键、查找与内存代价——

```text
H · C_body  >  C_key + C_lookup + amortized(C_mem)
```

否则容量保持 **0**。无证据时倾向不建或极小；有证据才增大容量。有界整数域等结构证据可计入 `H` / `C_lookup`，不另立机制。

**永久禁止整函数级 `T_f`** 若任一成立：

- `f` 的 `ε ≠ ∅`（体内纯区域仍可走 §7.4.1 与 §7.5.1-A）
- 已内联或体极小，使 `C_body` 不足以覆盖键与查找
- `C_key ≥ C_body`（键过大或不划算）
- 参数类型无法形成可靠键（实现拒绝为其提供键）
- Debug 配置选择关闭 runtime Memo（见 §7.5.5）

---

#### 7.5.3 `T_f` 的表示与容量

在硬顶内，选择使 `Cost` 更优的表示：**能完美下标则不下哈希；不能则固定容量关联表。** 布局细节（稠密数组、小槽、开寻址等）是实现自由度，不是第二套用户可见分层。

**容量**：默认 0；通过 §7.5.2 后取有界正容量；同一次执行内禁止扩缩抖动。满则驱逐；驱逐后行为仍正确。用户不可依赖 `N`、表示或驱逐策略。

**结构性递归**（强启发，仍属同一 `T_f`）：可识别的 `f(n: Int)` 且体依赖更小 `n` 时，优先下标表；硬顶外的参数不缓存或改用不下标的有界表 / 不缓存。

---

#### 7.5.4 作用域对照

| 场景 | 局部消重（§7.5.1-A） | 透明 Memo `T_f`（§7.5.1-B） |
| --- | --- | --- |
| 纯函数 | 可 | 可（仅当 §7.5.2 通过） |
| 效应函数体内的纯子表达式 | 可 | 否（除非拆成独立 `ε = ∅` 函数；自动 outline **不是**语义义务） |
| 效应函数整体 | 不适用整函数 Memo | 否 |

与 §7.4.1 一致：纯分析在表达式 / 基本块粒度进行；透明 Memo 只挂在整函数 `ε = ∅` 上。

---

#### 7.5.5 Debug / Release

- **Release**：按 §7.5.0～7.5.3 启用；默认低占用。
- **Debug**：可关闭全部 runtime `T_f`，仅保留局部消重中对调试无害的部分；**纯函数返回值**与 **效应顺序** 仍须与 Release 一致（§2.6）。
- 不得因 Memo 命中差异改变 §2 可观测合同。

---

#### 7.5.6 语义合同（清单）

1. 任意表示与容量不得改变纯函数返回值，不得改变效应顺序。
2. 用户不可依赖：是否建表、命中与否、容量、表示、驱逐策略（§2.5）。
3. 无 `memo` 关键字；无用户可见缓存 API。
4. 禁止无界全局 Memo 表作为默认或唯一路径。
5. 未命中路径开销有顶；失败时等价于直接调用（正确性），性能上受 §7.5.0 护栏约束。
6. 启发与 `α`、`β`、容量上下界宜**版本化**；改变不得静默破坏「默认低占用」承诺。

---

#### 7.5.7 设计理由

| 诉求 | 对应 |
| --- | --- |
| 严格求值、好调试 | 以局部消重为主；不靠惰性 thunk 当默认 Memo |
| 用户无感 | 全自动；无注解 |
| 统一 | 跨调用只有 `T_f` 一种机制 |
| 高效 | 硬顶内择优表示；避免无证据的大哈希 |
| 低占用 | 默认不建或极小；双硬顶；大表稀有 |
| 可辩护 | 建表由代价决定，而非固定多层菜谱 |

**一句话**：先证明同指；必须跨调用复用则建有界 `T_f`；表示与容量是参数；永远可关、可驱逐、命中非语义。

## 8. 错误处理

### 8.1 `Result` / `Option` + `alt` + 有限 `return`

- 可预期失败用 **`Result`**（`Ok` / `Err`），缺值用 **`Option`**；不用异常做控制流。
- **`alt`**：`expr alt rhs` / `expr alt { … }` — 成功取载荷，失败跑右侧（类型为载荷 `T`）。
  - `Result` 的块/右式中绑定 **`err`**；`Option` 无 `err`。
  - 与布尔 `or` 无关。
- **传播**：显式 `alt return Err(err)` / `alt return None`（不自动包装、无裸 `alt return`）。
- **`?` 后缀传播：搁置**。

```lumia
val load = { path ->
    val s = readFile(path) alt return Err(err)
    val n = parseInt(s) alt return Err(err)
    Ok({ port = n })
}

val head = { xs ->
    xs.first() alt return None
}

val port = m["port"] alt 8080
```

### 8.2 可恢复 vs 不可恢复


| 类型    | 机制                                    |
| ----- | ------------------------------------- |
| 缺值 / 局部恢复 | `Option` / `Result` + `alt`        |
| 可预期失败传播 | `alt return Err(err)` / `return None` |
| 编程错误  | `assert` / 模式匹配失败 → 栈追踪 + 终止          |
| 契约    | 可选 `requires`/`ensures`（后期），编译期或运行时检查 |

## 9. 模块、可见性与导入

### 9.1 模块

- **必须** 显式 `module` 声明（文件顶或约定位置）；不靠「文件名即模块」偷懒。

```lumia
module math.vector
```

### 9.2 可见性：默认 `pub`

- 语言中 **默认公开**（相当于处处 `pub`）。
- 需要隐藏时用 `**priv`**（或实现阶段定名的私有关键字）标模块私有。
- 不强制在公开 API 上写类型签名。

```lumia
module math.vector

val dot = { a, b ->        // 默认公开
    ...
}

priv val helper = { ... }  // 仅本模块可见
```

### 9.3 导入

```lumia
import a.b              // 导入单个
import a.{b, c}         // 导入多个
import a.*              // 导入全部
import a.b as bee       // 别名
import a.{b as bee, c}  // 多选中的别名
```

## 10. 标准库原则

- **小核心、厚标准库**：语言内置为语法与 **核心类型**（含 `List` / `Map` / `Set` / `String` 等）；I/O、字符串处理、集合上的厚 API 在 `std`。
- 标准库函数默认 **纯**；I/O 在 `std.io` 标记为效应 API。
- `List` / `Map` / `Set` API 全部接受 **统一用户类型**；不提供“性能版 duplicate API”（无 `HashMap` 导出给用户）。

## 11. 并发与并行（预留）

### 11.1 纯并行

- 编译器 / 运行时对 **证明无数据竞争的纯 `map`/`fold`** 自动并行。
- 用户不写 `parMap`。

## 14. 示例：完整程序

```lumia
module WordCount

import std.io.{readStdin, println}
import std.string.{split, trim}

val normalize = { line ->
    line
        >> trim
        >> split(' ')
        >> filter { w ->
            w.len() > 0
        }
        >> map { w ->
            w.toLower()
        }
}

val count_words = { lines ->
    lines
        .flatMap(normalize)
        .fold([:]) { acc, word ->
            acc.get(word) match {
                Some(n) -> acc.set(word, n + 1)
                None -> acc.set(word, 1)
            }
        }
}

val main = {
    val text = readStdin()
    val lines = split(text, '\n')
    val counts = count_words(lines)
    for (word, n) in counts.items().sortBy { p ->
        p.0
    } {
        println("${word}: ${n}")
    }
}
```

用户心智：逐行读、拆分、计数、排序、打印。  
编译器：`normalize` 管道可融合；`fold` 进 `Map` 可走 `SmallMap` → `HashOrdered` / `Overlay`；**语义 never 变**。
（若只要内容相等、不要求打印序，亦可直接 `for (word, n) in counts`——为插入序。）

## 15. 设计不变量 checklist

实现团队与优化 Pass 必须永远满足：

- 用户代码可零类型注解完整编译（完全推断）
- 无强制 `fn` 签名风格；函数即 `val` + `{ 参数 -> 体 }`（有参必写 `->`）；支持尾随闭包
- 管道符为 `>>`（`x >> f` ≡ `f(x)`）；`>>` 优先于 `match`；不用 `>>` 做移位
- 逻辑用 `and`/`or`/`not`；有限 `return`；`alt`；有 `break`/`continue`；单参闭包可用 `it`
- UFCS：`p.move(1,2)` ≡ `move(p,1,2)`
- 显式 `module`；默认公开；`import a.b` / `a.{b,c}` / `a.*` / `as`
- 列表 rest 模式为 `[x, ..rest]`；match 或模式用逗号
- 变体载荷：内联积与具名积都允许；本阶段无 `?` 传播
- 透明 Memo：仅 `ε = ∅`；唯一机制为有界 `T_f`；与局部消重（CSE/同指共享）区分；建表须过代价模型与硬顶；命中与否非语义；效应函数体内纯区域可局部消重，不可整函数跨调用 Memo
- 无 `while`；循环仅 `for in` / `for cond`
- 官方缩进 4 空格
- 无引用相等 API
- 无 `sizeof` / `capacity` 作为语言特性
- 纯表达式内零 I/O 效应（`var` 换绑允许并 SSA 化）
- 效应语句为可观测副作用最小单位；函数级 `ε` 仅为调用边界标签
- `main` 隐式效应根；日常不写 `effect { }`；`effect { }` 已实现为普通块别名
- 效应沿调用图静态传播；体内纯区域可优化，不自动 outline 为语义义务
- 模块顶层 `val` 初始化须纯；I/O 从 `main` 或效应函数进入
- 效应语句顺序可观测且保序
- 严格求值 + 文档化短路
- 单一 `List` 用户类型；单一 `Map` / `Set` 用户类型（无 Hash*/Tree* 分型）
- 集合正规构造为 `listOf` / `mapOf` / `setOf` / `range`；字面量与范围为糖；管道 `map` ≠ `mapOf`
- `Map`/`Set`：内容相等与插入序迭代；缺键为 `None`；表示选择非语义
- 模块顶层无 `var`
- 无 `Ref` / 无用户可见共享可变单元
- 无 `class` / 继承 / 对象同一性；无隐式 `this` 可变状态
- 数据唯 `type`：积用 `val` 字段，和用无 `val`/`var` 的变体；字段禁止 `var`
- 所有 Release 优化可证伪于 Debug 对照测试
- 无未定义行为

## 16. 开放问题（实现 / 语义 / 搁置）

1. **泛型编译模型**（实现）：单态化 vs 擦除 vs 混合 —— 不影响源码写法。
2. **整数溢出**（语义）：暂默认 **trap**；环绕 / 大整数以后可再议。
3. **包管理器**：命名与 lockfile（工具链）。
4. `**?` 错误传播**（语法糖）：**搁置** —— 当前用 `Result` + `match`；以后再定。

### 已决议语法（累计）


| 项                    | 决议                                                                |
| -------------------- | ----------------------------------------------------------------- |
| 短闭包                  | Kotlin 式 `**it`**                                                 |
| UFCS 点调用             | **要**                                                             |
| `break` / `continue` | **要**（仅 `for`）                                                    |
| `>>` 与 `match`       | **先 `>>`**                                                        |
| 模块                   | **显式 `module`**                                                   |
| 早期 `return`          | **有限**：最近函数/闭包；无非局部返回                                      |
| `alt`                  | **要**：Option/Result 恢复；传播写 `alt return Err(err)`                 |
| `?` 传播               | **搁置**                                                              |
| 透明结果复用               | **要**：局部消重 + 唯一跨调用机制有界 `T_f`（代价模型 / 硬顶择优表示）；默认低占用；无用户语法 |
| 变体载荷                 | **内联积与具名积都允许**                                                    |
| 逻辑运算                 | `**and` / `or` / `not`**；按位不用 `&` `                               |
| 函数双形态                | **都保留**                                                           |
| match 或模式            | **逗号** 分隔                                                         |
| match 臂体              | **表达式或块**；单表达式可不写 `{}`                                              |
| 无主体 `match { }`       | **要**（Kotlin `when { }`）；布尔多路；`_` 兜底且须最后                              |
| 导入                   | `import a.b` / `a.{b,c}` / `a.`* / `as`                           |
| 可见性                  | **默认公开**；隐藏用 `priv`                                               |
| 注释                   | `//` 与 `/* */`                                                    |
| 插值                   | `"${x}"` 与 `"$x"`                                                 |
| 类型注解                 | 罕用；`x: Int`                                                       |
| `effect { }`           | **要**：可选视觉分区；语义等同普通块（`main` 已是效应根） |
| `Map` / `Set`          | **要**：与 `List` 同哲学；正规 `mapOf`/`setOf`；糖 `[:]` / `[k : v]`、`#{}`；插入序；部分构建 |

| 表示选择纪律             | **要**：能证则特化，不能证则默认稳定路径（§7.1.1） |

## 17. 总结

Lumia 不要求用户在 **惰性/严格、Stream/Array、HashMap/TreeMap、pure/effect、栈/堆、类型注解** 之间做选择。效应由编译器推断：`main` 里直接写 I/O，无需手写 `effect`。

用户写：

```lumia
val add = { a, b ->
    a + b
}

var n = 0
n = n + 1
```

编译器负责：完全推断类型、SSA 化 `var`、`List`/`Map`/`Set` 表示变换、**透明结果复用（有界 memo）**、CSE/融合与并行。

这是 **Kotlin 的人体工学** 与 **Haskell 的可推理性** 的合取，而非折中：

- 要了 Haskell 的 **纯表达式 + ADT + 穷尽匹配 + 完全推断**
- 不要 Haskell 的 **全局惰性 + 显式 IO Monad + 类型签名文化**
- 要了命令式的 `**val`/`var`、书写顺序与 Debug 直觉**
- 不要 C/Java 的 **引用语义与实现细节泄漏**

**Lumia：写你所想，编译器证明其余。类型存在，但你不必写。**
